A Thesis on the Design and Delivery of seanburman.com

Abstract / Overview
--------------------
This document records the design and build conversation that produced
seanburman.com: a personal consulting site for custom business software and
automation. The work began as a new repository under B2B/seanburman.com,
seeded with UI reference imagery copied from a prior seanburman project into
docs/ui, and published to GitHub under seanbman/seanburman.com. The site
evolved from a dark SaaS-style landing page into a moody architectural
homepage, then gained a contact experience conceived as a digital calling
card rather than a lead-capture form. The stack is React and Vite with
react-router, deployed through GitHub Pages Actions on the custom domain
seanburman.com with a repository base path of /. This thesis synthesizes the
problem, approach, design decisions, implementation choices, deployment
lessons, and open questions that shaped the result.


Problem
-------
The practical need was a credible public presence for custom software
consulting: a place that communicates who Sean Burman is, what kind of work
is offered, and how to get in touch—without the clutter of a marketing site
or the friction of a contact form. Early work also had to leave Squarespace
DNS behind and land reliably on GitHub Pages. Along the way, operational
failures (the site “not loading,” branch-name mismatch after renaming master
to main) forced deployment correctness to become part of the design story,
not an afterthought. On the product surface, typography and layout had to
read as intentional on both mobile and desktop: a strong hero, clear copy,
and a contact card that favors real-world actions (call, email, save
contact, scan QR) over generic web patterns.


Approach
--------
The project proceeded in deliberate stages. First, the repository and remote
were established, inspiration assets were centralized under docs/ui, and an
initial React + Vite front page was built from landing_inspiration.png in a
dark SaaS visual language. GitHub Pages was configured for continuous
deploy. When the live site failed to resolve correctly, diagnosis moved from
application code to DNS and Pages configuration: Squarespace still owned the
domain records; a custom domain and CNAME were introduced; later, deploys
were blocked because the Pages environment still allowed only the master
branch after the default branch had been renamed to main.

Design then shifted from generic SaaS chrome toward architectural atmosphere.
The homepage was rebuilt around a dark, moody architecture hero, pairing
Cormorant Garamond for display type with Outfit for supporting UI text. Copy
was iterated until it stated a clear offer and a human byline. The default
branch rename (master to main) was completed and the architectural homepage
was merged. Finally, a dedicated contact route was designed as a digital
calling card—identity, role, phone, email, save-to-contacts, quick actions,
and a desktop QR—rather than a form that asks the visitor to write first.


Design Decisions
----------------
Brand and atmosphere take priority over dashboard-like density. The first
viewport is one composition: brand, one headline, one supporting sentence,
one call to action, and a full-bleed architectural image. The chosen headline
is: “Custom software, engineered for the realities of your business.” The
byline is: “I build practical software around the way your business works,
and the places where it could work better.”

Typography uses Cormorant Garamond and Outfit to avoid default system stacks
and to reinforce a serious, editorial consulting tone rather than a startup
template. The contact page continues that language as a calling card: the
name SEAN BURMAN (presented as Sean Burman in the UI), the role line “Custom
Business Software and Automation” (with ampersand preferred in layout),
phone +1 368 997 4329, email info@seanburman.com, an Add to Contacts (.vcf)
action, Call / Email / LinkedIn shortcuts, the same byline, and a QR code
intended for desktop so a visitor can open the card on a phone.

Responsive behavior encodes product principles. On desktop, the QR is
valuable and visible; Add to Contacts and Call are hidden because they are
less natural there. On mobile, those actions surface and spacing is tuned so
the card remains calm and usable. Typography orphans were treated as a
design defect: leaving “Automation” alone on a line was rejected, and the
preference settled on an ampersand with non-breaking spaces so that
“Software & Automation” stays together rather than orphaning “& Automation.”

That single case later hardened into a site-wide rule: no orphan words,
anywhere, at any width. The rule is enforced in two layers. First, CSS
text-wrap: balance on every heading and text-wrap: pretty on body copy and
list items lets modern browsers rebalance lines and avoid single-word last
lines on their own. Second, as a hard guarantee in all browsers, the final
word pair of every sentence-ending string — headlines, byline, column
bodies, pain items, step bodies, calls to action, the footer copyright —
is joined with a non-breaking space (for example "your business.",
"work better.", "is fixable."), so the last line always carries at least
two words.


Implementation
--------------
The application is a small React SPA built with Vite and typed with
TypeScript. Routing is handled by react-router, with a homepage at / and a
contact experience at /contact. Static assets live under public/, including
the architectural hero image, a sean-burman.vcf vCard, a contact QR SVG, and
a CNAME file declaring seanburman.com. Vite’s base is set to / because the
site is served from the custom domain apex rather than a project subpath.
The build script compiles TypeScript, produces the Vite bundle, and copies
index.html to 404.html so client-side routes resolve under GitHub Pages.

The contact page is intentionally not a form: it presents identity and
direct channels. Mobile-only CSS classes gate Add to Contacts and Call.
Desktop layout places the QR beside the card. Role-line markup uses
non-breaking spaces around an ampersand entity so “Software & Automation”
wraps as a unit. Inspiration screenshots remain in docs/ui for design
memory (landing_inspiration.png, homepage-inspiration.png, and related
dashboard and tool references).


Deployment Lessons
------------------
Several lessons arrived through failure. DNS that still pointed at
Squarespace made the GitHub Pages site appear “not loading” even when the
build was healthy; fixing the problem required registrar A records for the
apex (GitHub Pages IPs) and a www CNAME to seanbman.github.io, plus Pages
custom-domain verification and HTTPS enforcement. A CNAME file in the
repository is necessary but not sufficient without matching DNS.

Branch rename introduced a second class of outage. After renaming master to
main, GitHub Pages (or the Actions environment allow-list) still expected
master, so deployments were blocked until the environment was updated to
main. The durable rule is that branch policy, workflow triggers, and Pages
settings must move together when the default branch changes. The documented
operating model is: push to main, GitHub Actions builds and deploys, site
URL https://seanburman.com.


Contact Experience
------------------
The contact route is the product’s second chapter: from introduction to
introduction-of-self. It behaves like a digital calling card. Primary
signals are name, role, phone, and email. Secondary actions are Add to
Contacts (.vcf), Call, Email, and LinkedIn. The byline repeats the homepage
promise so the card remains coherent with the brand. The QR on desktop is
treated as a bridge from large screen to phone, not decoration. Mobile-first
action visibility (save and call) and desktop-first QR visibility encode the
assumption that the most useful action depends on device context. Layout and
spacing iterations on mobile were required to keep the card from feeling
cramped once those actions appeared.


Business Narrative (Below the Fold)
-----------------------------------
The homepage later grew beyond the single hero composition, answering one of
the open questions below. Three sections now scroll beneath the untouched
first viewport, and together they present a customer-facing account of what
the business actually is: not just making software, but identifying
bottlenecks, building efficiency, and shaping tools that conform to the way
a business already runs.

A deliberate vocabulary rule governs all of this copy: the word "consulting"
is never used, because the target audience — tradespeople and operators of
practical businesses — distrusts it. Also avoided: "solutions," "leverage,"
"streamline," "digital transformation." The allowed register is plain and
concrete: bottlenecks, time, paperwork, double entry, chasing invoices, the
way your business runs.

The three sections are:

1. "The work / More than building software." — three columns that describe
   the engagement in order: Find the bottleneck (watch how work moves through
   the business — crews, materials, and equipment as much as quotes,
   schedules, and invoices — and find where hours and money quietly
   disappear), Build the fix (software that removes that exact friction,
   sometimes a single automation, sometimes the system the whole operation
   runs on; never an off-the-shelf subscription), and Make it fit (the
   software bends to the business — in the office, in the truck, on the job
   site; if the crew needs a training seminar, the wrong thing was built).

   Two copy decisions were made deliberately here. First, the scope of the
   work is not capped at small tools: early copy said "a small, practical
   tool or automation," which read as though small utilities were the whole
   offer; the revision runs the range from one automation to an
   operation-wide system. Second, physical work is first-class: the language
   names crews, trucks, materials, equipment, and job sites alongside the
   admin flow, because the software serves businesses whose work happens in
   the field, not only at desks.

2. "Where the time goes / Sound familiar?" — a self-identification list of
   concrete, recognizable pains: job details typed into three places, quotes
   that take days because the numbers live in someone's head, paper job
   sheets that die in the truck, crews standing around because nobody told
   them the plan changed, chasing invoices at month end, a scheduling
   spreadsheet only one person understands. The list deliberately mixes
   field-coordination pains with paperwork pains. It closes with the promise
   that every one is a bottleneck and every one is fixable.

3. "Working together / How it starts." — a three-step, low-commitment
   process: a conversation (no pitch, no obligation), a close look (on site
   or over the phone), one small thing (a single tool that pays for itself
   before going further). The section ends with a "Start the conversation"
   call to action into the contact calling card.

The first viewport remains sacred: brand, headline, byline, one call to
action, full-bleed architectural image. The new sections continue the same
typography system (Cormorant Garamond display, Outfit body), separated by
hairline rules, so the page reads as one editorial composition rather than
a marketing brochure. Case studies remain deferred until real ones exist;
the "Sound familiar?" list does that job for now.

Scroll choreography was added on top of the narrative: a sticky
stacked-section parallax (also called a sticky overlap or section takeover
transition). The hero stage and each narrative section pin to the viewport
(position: sticky, top: 0, stepped z-index) and the next section slides up
and covers the pinned one, so the page reads as a deck of full-height
panels taking over from each other. Each panel is at least one viewport
tall so it fully covers its predecessor. The sections alternate grounds in
a black / white / charcoal rhythm: "The work" on black (#050505), "Sound
familiar?" on white paper (#f5f5f3) as the deliberate contrast beat where
the visitor recognizes themselves, and "How it starts" on charcoal
(#1f1f1d). The white panel inverts the text, muted-text, and hairline
tokens through scoped CSS variables rather than duplicated styles.

The effect works on every screen size, including mobile. The naive form of
this pattern breaks when a panel is taller than the viewport: pinned at
top: 0, its tail is covered by the next panel before it can be read. The
fix is a measured negative sticky offset — a small React effect
(useStackedPanels) measures each panel and sets top to
-(panelHeight - viewportHeight), so a tall panel scrolls fully into view,
pins only once its bottom edge reaches the bottom of the screen, and is
then taken over. Offsets are re-measured on resize and content changes via
ResizeObserver. No scroll libraries are used. Under
prefers-reduced-motion the panels return to normal document flow while
keeping the alternating grounds.

A slim footer band closes the page beneath the charcoal panel, returning
to the black ground: a copyright line and three quiet uppercase links —
LinkedIn, GitHub, and Contact. It participates in the same choreography,
sliding over the pinned final panel rather than sitting inside it.


Favicon and Icon Suite
----------------------
The original favicon was a leftover of the abandoned SaaS design (a
blue-purple geometric mark on navy) and was replaced with an on-brand
identity mark: the monogram "SB" set in Cormorant Garamond Medium,
off-white (#f5f5f3) on the site black (#050505). The letters were
converted to vector paths (via opentype.js against the Google Fonts
weight-500 TTF) so the icons are crisp at every size and independent of
webfont loading. The full suite lives in public/: favicon.svg (rounded
corners for browser tabs), favicon.ico (16/32/48), apple-touch-icon.png
(180, full-bleed square since iOS applies its own mask), icon-192.png and
icon-512.png for the web app manifest, and icon-512-maskable.png with
safe-zone padding (purpose: maskable). site.webmanifest declares name,
colors (#050505 for theme and background), and the icon set; index.html
links the ico, svg, apple-touch icon, manifest, and a theme-color meta.


Open Questions
--------------
Several questions remain open for future iteration. The homepage has now
grown beyond the single hero composition into a below-the-fold business
narrative; the remaining question is whether case studies should eventually
join it once real ones exist. Is the calling-card contact model
sufficient for inbound work, or will a lightweight scheduling or inquiry
path eventually be needed without becoming a conventional form? How should
typography and image assets be versioned as the brand system evolves—keep
inspiration under docs/ui, or graduate to a more formal design system? What
monitoring or redirect strategy is appropriate if DNS or Pages configuration
drifts again? Finally, as the site accumulates more routes and content, how
should context for assistants and collaborators be maintained—through
documents such as this thesis and machine-readable graphs derived from them?


Technical Summary
-----------------
Stack: React, Vite, react-router, TypeScript.
Hosting: GitHub Pages via GitHub Actions; base path /; custom domain
seanburman.com; repository seanbman/seanburman.com.
Design: dark architectural hero; Cormorant Garamond + Outfit; calling-card
contact; desktop QR; mobile-first contact actions; below-the-fold business
narrative (bottlenecks, fit, low-commitment start); no "consulting"
vocabulary; sticky stacked-section takeover scroll with black / white /
charcoal panel rhythm on all screen sizes (measured negative sticky
offsets for tall panels; static fallback under reduced motion only).
Copy anchors: headline “Custom software, engineered for the realities of
your business.”; byline “I build practical software around the way your
business works, and the places where it could work better.”; contact role
“Custom Business Software & Automation.”
